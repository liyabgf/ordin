# Ordin 工程执行纪律

本文件约束执行 [完整后续工程规划 v2](33-functional-execution-plan.md) 的所有 agent（主代理与子代理）；[工程分解 v1](30-engineering-plan.md) 只作历史范围映射。它是 [AGENTS.md](../AGENTS.md) 在施工场景的落地细则；冲突时以 AGENTS.md 红线（A1–A7）为准。开工前读本文与 AGENTS.md，每次开工先在 [账本](ledger.md) 登记（R1）。

## 一、工作包生命周期

每个工作包（WP）必须按顺序走完八步，缺一步不得声明完成：

| 步骤 | 内容 | 依据 |
| --- | --- | --- |
| 1. 开工登记 | 账本写 WP 编号、意图、允许修改与禁改文件清单 | R1、R2 |
| 2. 契约先行 | 接口、schema、类型定义先落盘并自审，再写实现；契约变更须同步更新受影响 WP | A6 |
| 3. 隔离实现 | 在 /tmp 隔离快照开发与运行；本体工作树只放已验收变更 | R3 |
| 4. 正负测试 | 新行为必须有正例与负例；修缺陷先有失败复现测试 | A5 |
| 5. 变异检验 | 新增关键断言做变异：改坏→预期红→还原→核哈希 | A5 |
| 6. 闸门 | `npm run check` 退出码 0，日志落盘 | A1 |
| 7. 证据落盘 | `docs/acceptance/<里程碑>/WP-编号.md`：命令原文、退出码、哈希、遗留项 | 第4档 |
| 8. 独立提交 | 一个 WP 一个 commit，可 `git revert` 回滚；不夹带其他 WP 改动 | R5 |

**禁改文件**：WP 合同未列出的文件、用户 state 目录、凭据、运行中的服务进程、`ordin/` 现役仓库。

## 二、状态与完成定义

### 2.1 五种状态

每个 WP 只允许五种状态，由 [engineering-status.md](engineering-status.md) 唯一记录：

```
未开工 → 进行中 → 待验收 → 完成(离线) → 完成(真实验证)
```

- **待验收**：离线 DoD 已满足，等用户检查点或真实凭据。
- **完成(真实验证)** 必须有对应工作包真实模型/Worker/渠道/浏览器的实际证据，不受旧 M3 编号限制；某一能力真实通过不推导全项目真实通过。
- 状态变更必须同时更新账本与 [engineering-status.md](engineering-status.md)——后者是唯一事实源，禁止在汇报里凭记忆报状态。

### 2.2 完成定义（DoD）

一个 WP 标记完成(离线) 必须同时满足：

1. 契约文档与实现一致（类型/接口已落盘）。
2. 正负测试齐全，且变异检验证明关键断言可失败。
3. 隔离快照全量 `npm run check` 退出码 0。
4. 证据文件落盘且被本次 commit 包含。
5. 独立 commit 存在，`git status` 干净。
6. `git diff --stat` 证明未触碰禁改文件。

缺任何一项标「进行中」，并在汇报中写明缺哪项。

### 2.3 依赖强制

[完整后续工程规划](33-functional-execution-plan.md)列出的依赖未达「完成(离线)」时，后继 WP 不得开工。例外：纯文档契约类 WP 可与依赖方并行起草，但合入前必须核对契约一致。

## 三、并行与文件边界

### 3.1 允许并行的组（文件边界不重叠）

- 以规划 v2 的阶段依赖与文件所有权为准；契约设计可与前置实现并行，不能提前宣称功能验收完成。
- F2 资产/技能/记忆只有在共享作用域与版本契约冻结后才能并行。
- F5 各页面可在 F5-A 交互合同冻结后按独立文件并行，共用面板入口由主代理整合。
- 子代理并行时，每个代理在账本登记自己的文件边界，互相不越界（R2）。

### 3.2 冲突处理

两个执行者需要改同一文件时，后申请者等待或拆分交付物。发现越界改动立即回滚该部分并在账本登记。

## 四、变更控制

### 4.1 范围变更

WP 的范围、验收标准或依赖变更：

1. 账本登记变更申请：改什么、为什么、影响哪些 WP 与里程碑。
2. 影响里程碑出口标准的，须经用户确认后才生效。
3. 更新 [engineering-status.md](engineering-status.md) 与受影响的 WP 证据文件。

### 4.2 紧急缺陷

阻塞当前闸门的缺陷允许先修后补录，但必须在同一轮补齐：账本、复现测试、变异、证据。连续两次未补录即升级为事故登记（docs/incidents.md）。

## 五、用户检查点

检查点以 [规划 v2](33-functional-execution-plan.md) 为准：

| 检查点 | 提交结果 |
| --- | --- |
| CP-F1 | 首家真实 Worker 的执行、验收、回报及失败/取消记录 |
| CP-F3 | 数据恢复、幂等、权限和故障矩阵 |
| CP-F2 | 真实资产/技能复用、记忆纠正和撤销 |
| CP-F4 | 跨入口身份和真实收发/回程 |
| CP-F5 | 正式面板逐页浏览器与用户验收 |
| CP-F6 | 三后端/渠道矩阵、安装升级恢复和发布候选 |

检查点必须汇报可复核结果；是否继续依据用户当次授权。**当前用户要求“规划完成后等命令”，故不得启动任何后续实现或真实验收。** 旧 CP-1～4 仅作历史记录，不与新检查点并行指挥。

## 六、工程特有红线

在 AGENTS.md 红线之上，施工场景追加五条：

1. **测试必须测真实接线点。** HTTP 行为走真 server 测试、面板行为走 VM 真代码或真浏览器；不允许只对内部函数断言后宣称功能可用。
2. **不允许删测试换绿灯。** 测试失败先解释失败原因（A3），不许跳过、删除或放宽断言。
3. **mock 通过不等于真实通过。** 离线/模拟结论只能标「完成(离线)」；真实模型、真实渠道、真实浏览器是独立验收。
4. **面板改动必须有行为级验证。** 不允许只做源码字符串存在性断言。
5. **不许用「后续再修」吞掉已知缺陷。** 已知缺陷必须登记（账本或 incidents），带复现路径；口头「以后修」不算记录。

## 七、进度追踪

- [engineering-status.md](engineering-status.md)：当前工作包状态和证据的唯一事实源，旧 WP 表仅历史映射。每次状态变更随工作包提交更新。
- [账本](ledger.md)：操作流水（先写后做）。
- [事故](incidents.md)：过程缺陷登记。
- 里程碑出口向用户汇报格式：完成 WP 清单（含 commit）、遗留项、下一里程碑计划、需用户决策事项。

## 八、收尾顺序（每轮）

账本补齐 → 事故登记（如有）→ engineering-status 更新 → 隔离闸门退出码 0 → 独立 commit。口头与对话中的完成声明不作数；以落盘文件与退出码为准。
